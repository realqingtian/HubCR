# D-007 安全执行策略

[English](d-007-security-enforcement.md) | **简体中文**

- 状态：`ACCEPTED`
- 批准日期：2026-08-08
- 决策负责人：产品负责人
- 阻塞：G-03 与 M4 扫描策略契约

## 背景

M4 将引入异步漏洞扫描和 SBOM 工作流。在定义任务、结果、API 或 UI 契约前，
HubCR 必须决定扫描状态是否改变 Registry 拉取授权。过早阻断拉取，会在准确性、
例外处理和恢复证据尚不存在时，把 Registry 可用性绑定到扫描器的新鲜度与失败行为。

## 决策

首版 M4 策略仅提供信息展示：

1. Push 和 Pull 授权不依赖扫描是否可用、扫描状态、结果时效、漏洞严重级别或失败。
2. 扫描保持异步，绝不进入同步 Push 或 Pull 路径。
3. API 和 UI 如实表达 `QUEUED`、`RUNNING`、`COMPLETED`、`FAILED` 和 `STALE`。
   缺失、失败或过期的结果不得展示为安全。
4. 扫描结果与 SBOM 绑定不可变 Artifact Digest，而不是可变 Tag。
5. 可选或强制拉取阻断必须另行决策，并提供扫描准确性、时效限制、扫描器故障行为、
   管理员例外与审计流程，以及 Registry 可用性的实测证据。

本决策不批准严重级别阈值、fail-open 或 fail-closed 行为、仓库级执行策略，或同步安全门禁。

## 备选方案

- 仓库级可选阻断：推迟，因为仓库级安全策略的归属与例外行为尚未定义。
- 按严重级别强制阻断：推迟，因为首版扫描器还没有已批准的时效、误报、例外或可用性契约。
- 在结果缺失、过期或失败时 fail-closed：首版 M4 不采用，因为扫描器或任务故障会成为
  尚未验证的 Registry 故障机制。
- fail-open 执行：首版 M4 不采用，因为一边声明策略已执行、一边绕过失败检查会产生误导。

## 影响

- M4 可以在不改变 Registry 可用性的前提下，建立持久任务、Digest 绑定结果、重试、
  过期状态、API 和 UI 证据。
- 产品界面必须把结果描述为观测信息，而不是权限决策，也不能保证 Artifact 安全。
- 后续执行策略在改变 Pull 授权前，必须定义策略归属、例外、审计、时效、失败语义以及
  发布与恢复方案。
