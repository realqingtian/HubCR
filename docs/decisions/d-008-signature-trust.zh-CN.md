# D-008 签名信任

[English](d-008-signature-trust.md) | **简体中文**

- 状态：`ACCEPTED`
- 批准日期：2026-08-08
- 决策负责人：产品负责人
- 阻塞：G-03 与 M4 签名验证 Schema

## 背景

Cosign 同时支持公钥验证和无密钥证书身份。M4 持久化验证结果前，HubCR 需要明确的
长期信任模型。签名存在、密码学有效和策略信任是不同事实；把它们合并，会使后续策略
变更和历史解释变得不可靠。

## 决策

首版 M4 模型是每个 Namespace 一份版本化信任策略，由组织或个人 Namespace
所有者管理，并由该 Namespace 下的 Repository 继承。仓库级覆盖推迟。

每份策略可以包含以下一种或两种明确的信任主体：

1. 由不可变公钥指纹识别的公钥记录。HubCR 只保存公开验证材料与元数据；私有签名
   密钥绝不进入 HubCR。
2. 由精确 OIDC Issuer 与精确证书 Subject 组合识别的无密钥身份。

首版不支持通配身份或隐式信任。验证异步执行并绑定 Artifact Digest。结果记录签名
Artifact 标识、签名者证据、密码学有效状态、策略信任状态、信任策略版本、验证时间和
机器可读原因。依赖或透明日志服务不可用必须与签名无效和不受信任分别表示。

策略变更创建新版本并排队重新验证，不重写历史证据。本决策只定义证据与信任评估，
不批准 Pull 阻断。

## 备选方案

- 部署级单一固定公钥：不采用，因为它无法表达独立的组织归属，并会为后续无密钥支持
  带来破坏性的 Schema 迁移。
- 仅支持公钥：不采用，因为它排除了现代签名工作流使用的精确 OIDC 工作负载身份。
- 仅支持无密钥身份：不采用，因为自托管和离线公钥工作流仍是有效的部署需求。
- 首版支持仓库级信任策略：推迟，避免在 Namespace 级证据出现前引入策略优先级和
  管理复杂度。

## 影响

- M4 Schema 必须分离签名发现、密码学验证和策略信任，并全部按不可变 Artifact Digest
  建立关联。
- 策略轮换后仍可解释历史信任决策，因为结果引用明确的策略版本和签名者证据。
- UI 和 API 必须区分无效签名、有效但不受信任的签名者、验证依赖不可用、缺失签名和
  可信签名。
- Namespace 所有者可以使用公钥、精确无密钥身份或两者组合，但首版不能使用通配
  Subject。
